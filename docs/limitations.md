# Known limitations

The analysis errs on the side of silence: when a check cannot be decided exactly, nothing is
reported. The gaps below are known and deliberate trade-offs or not yet implemented.

- **Type checking** is conservative, not a javac equivalent: mismatches are reported only when
  every type involved is known, never through raw types, `var`, implicitly typed lambda parameters
  without a target, members inherited through a raw supertype or unsolved inference variables.
  `unchecked` warnings skip `var`, diamonds, inferred generic calls, lambda parameters, generic
  array creation and varargs declarations. Module visibility is checked only for imports in main
  sources of modules with a `module-info.java`, not against automatic modules. Blank `final`
  fields read inside lambdas and local / anonymous classes are not checked.
- **Generic inference**: type parameters that cannot be inferred stay unknown (no error, but some
  completions may be missing).
- **Nullness** tracks locals, parameters and `@Nullable` fields of `this` within a method; other
  fields and `@Nullable` calls use a heuristic. Scope defaults are not inherited by overrides,
  cover only parameters and return values, and for library classes come only from the same jar's
  `package-info.class`.
- **Lombok**: of `lombok.config` only accessor, logger-name and `stopBubbling` keys are applied;
  members generated by other in-memory annotation processors are not recognized.
- **Formatting** never joins lines, wraps only at list, chain, operator and `=` boundaries (filling
  lines, not one element per line) and never splits string literals.
- **Refactorings** are single-step without a dialog: pull up requires the method not to use members
  of the classes it leaves, extract interface takes every public non-override method, and there is
  no "move to arbitrary class". Change signature does not update lambdas implementing the method,
  Javadoc `{@link}`, explicit type arguments at calls or implicit `super()` calls.
- **Spring**: only beans defined in workspace sources are seen (so a missing bean is never
  reported); `@Profile` / `@Conditional…`, custom qualifiers and XML / programmatic beans are
  ignored. YAML without anchors or flow syntax; keys below `List<Pojo>` / `Map<String, Pojo>` are
  not completed or checked. HTTP client interfaces are linked to shared contracts by simple name.
- **Projects**: Gradle build scripts are not analyzed; Eclipse projects in different workspace
  roots are not linked to each other; generated sources are not split into main and test. Maven
  version ranges resolve against versions already in the local repository; nearest-wins arbitration
  does not re-check hard ranges (direct `lib:1.0` vs transitive `lib:[1.1,2.0)` keeps 1.0); remote
  metadata is not consulted until the Maven fetch fallback runs. Duplicate classes on the class
  path use the first jar's copy for stubs and subtype tables, and Spring configuration files
  resolve types globally. Source files that are not open in the editor are decoded with their
  module's source encoding, except that a file which is valid UTF-8 is always read as UTF-8 (many
  projects declare GBK but contain only ASCII or UTF-8); modules without a recognized encoding,
  Spring configuration files, `lombok.config` and `.editorconfig` are read as UTF-8 (invalid bytes
  become U+FFFD). The server never writes workspace files itself, so edits to closed files are
  saved by the editor in the encoding it uses for them.
- **Libraries**: sources are analyzed against the project's class path (JDK-internal classes left
  out of `ct.sym` stay unresolved in JDK sources). Without a sources jar — downloaded on demand only
  for jars in a Maven repository or the Gradle cache — parameters show as `arg0`, `arg1`, … and the
  class opens as a decompiled stub; about 0.4% of JDK method bodies cannot be decompiled.
- **Debugger**: does not build the project; evaluation does not support assignments, lambdas or
  anonymous classes, invokes methods only on threads stopped by a breakpoint, step or exception,
  and aborts calls after 5 seconds (on some JDKs, such as 11, a call stuck in a loop cannot be aborted). Hot swap is triggered manually and, as in the JVM, cannot add or
  remove methods and fields. Collections show their fields rather than a logical view; function
  and data breakpoints are not supported.
